Threadpilot

Adaptive concurrency for Ruby. One gem. Zero config changes. Faster apps.

Your Thread Count Is Wrong

Every Ruby application server asks you to pick a thread count. Five threads? Ten? Twenty? You pick a number, deploy it, and hope for the best. But your workload isn't static. Traffic patterns shift throughout the day. Some requests hit the database for 200 milliseconds. Others crunch numbers in pure Ruby. The right thread count for one is the wrong thread count for the other.

When your workload is I/O-heavy, you need more threads to keep the CPU busy while requests wait on the network and disk. When your workload is CPU-bound, extra threads just pile up behind the GVL, adding queueing delay and inflating your tail latencies. You've been forced to pick one number and live with the compromise.

Until now.

Runtime Concurrency, Automatically Tuned

Threadpilot observes your application's actual GVL utilization in real time and adjusts your thread count to match. It uses the GVL instrumentation API introduced in Ruby 3.2 (via the gvl_timing gem) to measure how much time threads spend waiting for the lock versus waiting on I/O.

When Threadpilot detects that your workload has shifted toward I/O-heavy requests, it scales threads up so more work proceeds in parallel. When it detects rising GVL contention, a telltale sign of CPU-bound work, it scales threads back down to eliminate queueing delay. The result is an application that adapts continuously to whatever your users throw at it.

No cron jobs. No manual tuning. No restarts required.

Two Problems, One Solution

Higher throughput when I/O dominates. Database queries, HTTP calls to third-party services, reading from disk: these are all moments where the GVL is released and other threads could be doing useful work. Threadpilot ensures you have enough threads to fill those idle gaps, even when the I/O burst is temporary and transient.

Lower tail latency when CPU dominates. When threads compete for the GVL, each one waits in line before it can run. This queueing time shows up directly in your p95, p99, and beyond. Threadpilot detects this contention pattern and reduces thread counts, cutting the queue and bringing those tail latencies back down.

Most applications experience both patterns, sometimes within the same minute. Threadpilot handles the transitions for you.

Drop-in installation

Add the gem, configure your min and max thread bounds, and let Threadpilot do the rest. Works with Puma out of the box.

Built on public APIs

Uses Ruby 3.2+'s GVL instrumentation API. No monkey-patching. No C extensions beyond what Ruby itself provides.

How It Works

Threadpilot runs a lightweight background loop that samples GVL timing data at a configurable interval. From these samples, it computes an I/O wait ratio: the fraction of wall-clock time your threads spend waiting on I/O versus holding or waiting for the GVL.

When the I/O wait ratio is high, the application benefits from more concurrency. Threadpilot nudges the thread count upward. When the ratio drops, indicating CPU-bound work and GVL contention, Threadpilot brings threads back down. The adjustments are bounded by your configured minimum and maximum, and rate-limited to avoid oscillation.

The overhead of the instrumentation and control loop is negligible. GVL timing hooks are maintained by the Ruby core team and designed for production use.

Requirements

Threadpilot requires Ruby 3.2 or later (for GVL instrumentation) and MRI/CRuby. It works with any threaded application server. Puma integration is included and requires zero configuration beyond adding the gem.
