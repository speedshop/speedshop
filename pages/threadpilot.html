Nobody understands the GVL

The problem is that picking the right number of threads in a threadpool is very hard. Getting this answer correct requires extensive knowledge of the Global VM Lock (GVL), and in-depth observability in production which gives you a sense of your workload's I/O characteristics.

Maybe you read a Github issue that was a hundred comments long and realized that not even some of the most experienced Rails developers in the world could agree on a single "best" number. Maybe you accidentally crashed your Sidekiq process because your database pool wasn't set to the same number as your concurrency configuration. There's a nagging sense that this all ought to be easier.

Even Mike Perham (the author of Sidekiq) and Rails core members like byroot have changed their minds on the "right" number over the years. The defaults for Puma and Sidekiq have changed over the years - why? Who can stay on top of all of this?

Too few threads? You're wasting money.

When a request waits on the database or an upstream API, another thread can do useful work. Too few threads leave that opportunity unused. Threadpilot can add concurrency instead of leaving requests waiting for a free thread.

You don't need to know your exact I/O percentage to explore this. Pick the thread count you run today, then change the workload. The same baseline follows you through all three illustrations.

Too many threads? More isn't always better.

When Ruby CPU work dominates, extra threads compete for the same GVL. A larger pool can add processing latency without adding throughput. Threadpilot can shrink the pool while keeping useful work moving.

It wasn't possible until now

Changing runtime concurrency is actually a fairly complicated technical problem.

The instrumentation required to get this right didn't exist until Ruby 3.2. Now, thanks to Ruby contributors, we can actually observe when threads queue for the GVL, which provides the critical backpressure required for auto-tuning to work.

Puma and Sidekiq also didn't support the idea of changing thread counts at runtime. Now, after our contributions to Puma, that project now supports it. We also figured out how to make it work for Sidekiq.

Threadpilot: automatic thread tuning for Puma and Sidekiq

So, Yuki and I built this Rubygem. You install it, change a half-dozen lines of config, and then watch all of your Puma and Sidekiq processes get more efficient.

Threadpilot adjusts concurrency at run-time based on your workload's actual demands. In a Ruby runtime with a Global VM Lock (GVL) such as MRI/C Ruby, this means that Threadpilot leads to:

  • Improved throughput. I/O-heavy workloads (even when transient or temporary) will be given more threads, leading to more work being done in parallel.
  • Reduced latency. When workloads are CPU bottlenecked, Threadpilot detects GVL contention (queueing for the GVL) and reduces thread counts, leading to lower latency, particularly in the ~p95+ range.

Threadpilot uses the gvl_timing gem (a wrapper around the Ruby 3.2+ public GVL API) to collect GVL timing data and measure I/O wait ratios.

FAQ

What version of Ruby do I need?

Theadpilot supports CRuby 3.2 and above. This is because we use the new GVL instrumentation APIs added in that version.

Will Threadpilot increase my memory usage or cause malloc arena fragmentation?

Potentially! Increasing thread counts will increase memory usage. We recommend running with jemalloc as your allocator, which mitigates a lot of the memory usage that comes with threading. But Threadpilot is designed to optimize the tradeoff between memory and throughput - it picks only the minimum number of threads necessary to get ~95% of the maximum possible throughput, meaning your thread count is never unnecessarily high.

Do I need to set my ActiveRecord connection pool size to match the max thread count?

Yes. We cover this extensively in our setup docs. Briefly: we recommend turning off ActiveRecord's connection pool maximum and using an external database connection pooler like PgBouncer, as higher threadcounts may lead to higher database connection count needs.

Is it safe to use in production? What if it picks a bad thread count?

Threadpilot has been extensively tested in production by the companies you see on this page, which process billions of requests per day. It's battle-tested and hardened against all kinds of weird production scenarios.

Does Threadpilot work on shared hosting platforms like Heroku, Render, or Fly?

Yes. GVL behavior is mostly independent of the underlying implementation, so even in a Docker container with 0.25 cpu allocated, we'll still work correctly.

My workload is mostly CPU-bound. Will Threadpilot still help?

Unless your workload is 100% CPU bound all the time (i.e. your code only runs Ruby and never performs IO of any kind, even logging) then Threadpilot will choose a better thread count than just single-threading. The exact answer depends on the workload - exactly what we wrote Threadpilot to fix.

Does Threadpilot work with Sidekiq Enterprise? What about capsules?

Threadpilot respects your Sidekiq Enterprise licensed thread-count. It works for any number of capsules in a process.
